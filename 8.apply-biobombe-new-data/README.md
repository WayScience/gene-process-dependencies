# Apply BioBombe to new data

## Purpose

This module applies the trained BioBombe ensemble to new, external gene dependency data.
The new data are DepMap-like: CRISPR gene knockout dependency scores, one row per sample and one column per gene, the same modality the ensemble was trained on.
Unlike `5.RNAseq` and `6.collab-data`, this module doesn't bridge across modalities — it runs new samples through the saved models directly.
The output is a set of latent scores per sample per model, annotated with the same GSEA pathway and drug correlation context used everywhere else in this project, so a new sample's vulnerabilities can be interpreted the same way an existing DepMap cell line's can.

The pipeline itself (`0` through `5`) is generic: any new dataset that can be shaped into samples-as-rows, genes-as-columns dependency scores can be run through it. The Largaespada lab MPNST screen is the one example dataset currently configured — its paths and filenames show up below as concrete illustrations of the pattern, not because the module is specific to it. Running a second dataset through this module means pointing the same path variables (set in each script's first cell or two) at that dataset's own `data/<dataset>/` directory and writing whatever `0.preprocess_raw_data`-equivalent step it needs; nothing else should have to change.

## Contents

### `utils/data_prep.py`

The shared functions every numbered script below builds on: loading new data, resolving its gene identifiers against DepMap's, formatting it both ways, and fitting, persisting, and applying the training scaler.
`prepare_new_data_for_biobombe()` chains all of that into one call — load, assess overlap, format both ways, scale — for anyone who wants the finished, model-ready data without stepping through it, which is what `2.format_and_scale_data` itself calls; `1.load_and_assess_gene_overlap` calls the loading and overlap-assessment pieces directly, since its job is to surface that report on its own before scaling ever happens.

### `0.preprocess_raw_data`

The one genuinely dataset-specific step: converts whatever a new dataset actually arrives as into the shape every other script in this module expects (one row per sample, one column per gene, a `ModelID` column, gene columns named to match DepMap's current symbols). Every new dataset needs its own version of this step, since "whatever it arrives as" varies by delivery; everything from `1.` onward is written against that shared output shape, not against any one dataset's raw format.

**Current example: the Largaespada lab MPNST data**, delivered as a samples-as-rows, genes-as-columns dependency matrix with current HGNC gene symbols already rescored against the correct DepMap release BioBombe was trained on (`data/largaespada/raw_data/`). That rescoring's provenance: [CStehn/MPNST-Synthetic-Lethal-Screen](https://github.com/CStehn/MPNST-Synthetic-Lethal-Screen)'s `chronos_24Q2_harmonization/chronos_24Q2_calc.py` co-models these local Brunello synthetic-lethal screens together with the full public DepMap 24Q2 Avana release (the same release this project's own `0.data-download` is pinned to) as one two-library Chronos model, exporting only the local screen rows — a batch-corrected gene-effect re-fit anchored to BioBombe's own training cohort, not just a relabeling of the original scores. That repo does its own independent gene-symbol harmonization (Avana's `"SYMBOL (entrez)"` stripped to plain symbol; outdated Brunello symbols resolved via HGNC's `prev_symbol`/`alias_symbol` cross-reference) before this data ever reaches `gene_effects.csv`, which is why the 31-gene residual below is this small. Of BioBombe's 2,718 trained genes, 2,701 already match this file's columns under their current symbol directly. The remaining 17 (`C7orf50`, `CCDC115`, `CENPJ`, `CIR1`, `FAM136A`, `FAM210A`, `FAM83H`, `FAM98B`, `N6AMT1`, `NCL`, `NEPRO`, `PRPF4B`, `SPATA5`, `SPATA5L1`, `TBRG1`, `TBRG4`, `TMEM199`) go through the same mygene.info-based harmonization logic the module uses generally: for each trained gene still missing under its current symbol, ask mygene.info for that gene's own former names, then check for an exact match among the raw column names — entrez id as the stable bridge across renames. Resolution works backward from the trained genes missing their current symbol rather than forward from the raw data's columns, since the forward direction hits genuinely ambiguous aliases shared by unrelated genes (e.g. "STRA13" names both CENPX and the unrelated BHLHE40) with no principled way to pick. For this particular dataset none of the 17 resolve via any known alias.
This step also checks for a second, different kind of missingness an alias lookup can't catch: `gene_effects.csv` carries a placeholder column for every gene in its own reference set rather than omitting ones outside this screen's guide library, so a trained gene can have a column that matches its current symbol exactly while every value in it is still NaN. For this dataset, 14 more trained genes (`CALM2`, `CARS2`, `CDK8`, `COQ4`, `KAT6A`, `MED20`, `PPP2R3C`, `SGO1`, `SPRTN`, `TAB2`, `TXNL4A`, `CENPX`, `KAT14`, `SARS1`) turn out to be entirely NaN this way, for a combined 31 / 2,718 trained genes with no usable value anywhere in the raw data. Both failure modes most likely mean this MPNST-specific screen used a different, smaller guide library than DepMap's genome-wide Avana library (consistent with a near-universally essential gene like `NCL` being among them), not a resolution failure. The combined list, with which of the two reasons applies to each gene, is written to `data/largaespada/results/genes_missing_in_raw_data.parquet` each time this runs, so it stays current if the raw data or BioBombe's trained gene set ever changes. `2.format_and_scale_data` imputes all of them with the training-split mean, same as any other gene missing from a new dataset.
Writes `NF1_data.parquet` and `NF1_metadata.parquet` to `data/largaespada/` for this example — a different dataset would write its own equivalently-shaped output under its own `data/<dataset>/` directory, with `1.load_and_assess_gene_overlap` and `2.format_and_scale_data` pointed at it instead.

### `1.load_and_assess_gene_overlap`

Loads the new dataset and compares its gene membership and column order against `CRISPRGeneEffect.csv`.
DepMap gene identifiers and any new data's gene identifiers aren't guaranteed to match by construction, so this step is not a formality: it reports how many genes overlap, how many are missing on either side, and whether shared genes are already aligned in the same order.
It writes a gene-overlap report and a missing-gene list to the dataset's own `data/<dataset>/results/` directory, which later steps in this module can read before trusting any join.

### `2.format_and_scale_data`

Formats the new data two ways, via `data_prep.prepare_new_data_for_biobombe()`: once aligned to the full DepMap gene set and column order, and once subset and reordered to the genes in the exact order the saved models expect.
Computes a `MinMaxScaler` from `1.data-exploration/data/VAE_train_df.parquet`, the exact 670-model train split the ensemble was actually trained on (not DepMap's full ~1150-model `CRISPRGeneEffect.csv` — fitting on the broader cohort gives measurably different min/max values for roughly 40% of genes, which showed up as new data scaling outside [0, 1] and breaking NMF, which requires non-negative input), and persists it to `results/depmap_gene_scaler.joblib`.
Every downstream script in this module (and any future dataset run through it) reuses that one persisted scaler rather than refitting on new data, since refitting would rescale relative to the new cohort instead of the training distribution the models actually learned.
Genes the trained ensemble expects but the new data doesn't have are imputed with the training-split mean for that gene, not dropped, so every sample still has a value for every trained gene going into the ensemble.

### `3.sanity_check_distribution`

Answers one question — is this new data reasonable to run through this pipeline? — in four parts, ordered cheap-and-definitive to expensive-and-suggestive, ending in an explicit conclusion rather than leaving it to be inferred from a column of numbers.

1. **Per-gene sanity on the raw, pre-scaling values**, restricted to the trained genes specifically: overall value distribution, missingness, and a range check flagging genes whose span looks implausible relative to the training data. For the Largaespada example, every flagged gene turns out narrower (never wider) than train's range for that gene — the expected artifact of 8 samples vs. 670, not a unit mismatch.
2. **Position relative to the training cohort** (`1.data-exploration/data/VAE_train_df.parquet`, not DepMap's broader ~1150-model cohort, since the training split is the exact population the persisted scaler was fit on and what "in-distribution" means here), checked two ways that don't agree equally well: a shared UMAP (coordinates saved for a later R figure), and nearest-neighbor distance through the actual saved BioBombe PCA models at a few latent dimensionalities, relative to how far training samples typically sit from each other. UMAP suggests the new samples sit apart from training; the more trustworthy PCA check (a fixed map, not re-fit jointly like UMAP, which is known to exaggerate separation between small groups) disagrees — ratios settle to roughly 0.9–1.6 by 10-50 components, not meaningfully more isolated than ordinary training variation.
3. **Biological plausibility specific to this dataset.** DepMap has 7 MPNST lines overall; only `HS-Sch-2` is in the train split (the other 6 were excluded by an age-metadata filter or landed in validation by chance, not for lack of relevance), so this part pulls all 5 DepMap MPNST lines with CRISPR data directly from `CRISPRGeneEffect.csv` and scales them with the same persisted scaler. A permutation test, run per new line (not pooled, since a pooled statistic can hide that some lines look MPNST-like while others don't), asks whether each new sample's mean pairwise PCA-space correlation with those 5 lines beats 10,000 random 5-line draws — at 50 components, `iPN3D` (p=0.0016) and `iPN2J` (p=0.034) are significant, `iPN1L`/`iHSC1L_F12`/`STS-26T` border on it, and the tumor-derived lines (`S462`, `ST88-14`, `iHSC1L_C3`) show no signal — notably the iPSC-derived lines, not the tumor lines themselves. Separately, the one new sample sharing a name with an existing DepMap line (`S462`, matched via `Model.csv`'s `StrippedCellLineName`) is checked for whether its raw dependency profile actually correlates with that specific line more than with DepMap broadly: r=0.689, ranking 340th of 1,150 (71st percentile) — elevated, consistent with real similarity, but not a standout identity confirmation on its own.
4. **Conclusion**, printed directly rather than left implicit: this data is in the right scale and format, not pathologically out-of-distribution relative to training, and shows plausible (if uneven) biological similarity to DepMap's own MPNST lines — reasonable to analyze with this pipeline, but at the edge of the training cohort's dense region, so results should be read as extrapolation from a narrow biological niche, not confident interpolation.

### `4.apply_biobombe_ensemble`

Loads each saved model from `3.run-biobombe/saved_models/` and applies it to the new data one at a time — `.transform()` for PCA/ICA/NMF, `.encode()` for the VAE variants — the same per-model-type dispatch `utils/model_utils.py` already uses elsewhere in this project.
NMF needs this clipped: it's the one model type that strictly requires non-negative input, and new data genuinely out-of-distribution for a gene (its value outside DepMap's training range for that gene) scales to slightly below 0 even with a correctly-fit scaler, since `MinMaxScaler.transform()` doesn't clip. `utils/model_utils.py`'s `extract_latent_dims` floors values at 0 for NMF specifically — not for PCA/ICA/the VAE variants, which have no such requirement, and not an upper-bound clip either, since NMF has no upper-bound requirement. For the Largaespada example this touched 116 of 21,744 scaled values (103 of 2,718 trained genes), mostly by a small margin (median -0.086); it's a no-op for any already-in-range value, so it doesn't affect the original DepMap train/test data this function was written for.
Writes one combined latent-scores table to the dataset's results directory (`NF1_data_latent_scores.parquet` for the Largaespada example), covering every model, latent dimension, and initialization in the ensemble.
Building this surfaced a real bug in `vvae_extract_latent_dimensions` (`2.prototype-VAE-models/utils/vanillavae.py`) that would have crashed on every VanillaVAE model in the ensemble — a signature mismatch with its caller, plus a numpy/tensor type mismatch inside the function — both fixed as part of this module, since they block inference for an already-trained model, not just training.

### `5.annotate_latent_scores`

Links each new sample's latent scores to the GSEA pathway results (`3.run-biobombe/gsea_results/`) for the corresponding model and latent dimension, via `utils/pinwheels.py`'s `assign_unique_latent_dims` / `compute_and_plot_latent_scores` — the same functions `6.collab-data/scripts/3.pinwheel_plots.py` uses for collaborator data.
Drug annotation follows the same pattern against `4.drug-dependency/results/combined_latent_drug_correlations.parquet` when that file exists; it's produced by `4.drug-dependency/scripts/5.drug_latent_dim_correlation.py`, which only became runnable once the BioBombe ensemble was downloaded, so this step skips drug annotation with a clear message rather than failing if it hasn't been generated yet.
Produces a per-sample ranked table of top associated pathways (and drugs, when available) in the dataset's results directory. It calls `compute_and_plot_latent_scores` with `make_plot=False` throughout, so despite `visualize/pinwheels/` existing as a gitignored path below, no pinwheel plot is actually generated yet — turning plotting on for each sample is still open.

## Data

`data/` holds whichever new dataset this module is currently applied to (its untouched delivery under `data/<dataset>/raw_data/`, plus `0.preprocess_raw_data`'s output alongside it), that dataset's intermediate and final results (`data/<dataset>/results/`), and figures (`data/<dataset>/visualize/`). `largaespada` is the one example populated so far.
It's gitignored for now, the same way `0.data-download/data/` is: no dataset run through here is ready to share yet, so it stays local until that changes.
`visualize/pinwheels/` is gitignored for the same reason, for whenever per-sample pinwheel plotting is actually turned on (see `5.annotate_latent_scores` above).
The persisted scaler in `results/` is the exception — it's derived purely from DepMap's already-public training data, not from any new dataset, so it's safe to commit and reuse across whatever new data comes next.
